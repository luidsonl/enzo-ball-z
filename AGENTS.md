# AGENTS.md — EnzoBallZ

Instructions for coding agents (OpenCode, Claude Code, Codex, Cursor, etc.)
working in this repository. Also read:

- `docs/SPEC.md` — game rules and balancing.
- `docs/ARCHITECTURE.md` — harness, contracts, and module boundaries.
- `docs/ACTIONS_AND_SKILLS.md` — action slots, modular skills, and mobile controls (plan + implementation status).

## 1. The project

EnzoBallZ is a 2D platformer in the style of Mario, written in Rust and compiled
to WebAssembly. Enzo runs, jumps, performs a physical combo, farms aura by
alternating `6`/`7`, and spends aura on the **Mogging** special. Enemies grant
XP; leveling up distributes points into Speed, Strength, Health, and Aura.

The MVP is single-player, but the core is designed for N players and for a
future authoritative server.

## 2. Stack and environment

- Rust 1.92.0 (edition 2021), Cargo workspace.
- Client: `macroquad` + `wasm-bindgen` (target `wasm32-unknown-unknown`).
- Local development server: Node 24, no dependencies.
- No external test framework in the core; use native `#[test]`.
- No third-party assets: sprites are generated by script.

## 3. Commands

```bash
# Quality and tests
cargo fmt --all
cargo clippy --workspace --all-targets -- -D warnings
cargo test --workspace

# Headless simulation
cargo run -p enzo-sim -- --ticks 600

# WASM build
rustup target add wasm32-unknown-unknown
npm run build
npm run dev
```

Always run `cargo test` and `cargo clippy` before committing. If the WASM build
fails due to a missing toolchain, record the blocker in the commit/PR instead of
hiding the error.

## 4. Structure

```text
crates/enzo-core/   pure simulation (physics, map, entities, mechanics, skills, aura, progression)
crates/enzo-wasm/   client: macroquad, input, render, HUD, save
crates/enzo-sim/    headless harness for replays and CI
assets/             original sprites and maps
docs/               spec and architecture
scripts/            WASM build, local server, sprite generator
web/                HTML and miniquad/macroquad JS plugins
```

Current core layout (action slots / modular skills):

```text
crates/enzo-core/src/
├── input.rs          # InputAction, ActionSlot, SlotInput, PlayerCommand
├── mechanics/        # walk, sixseven, combat helpers (outside skill slots where applicable)
├── skills/           # SkillId/registry, requirements, loadout, and one module per skill
└── entities/         # Entity with locomotion + skills, store/spec/controllers/projectiles/items
```

Current client render layout:

```text
crates/enzo-wasm/src/render/
├── world.rs          # orchestration only
├── entities/         # character/entity body animation and drawing
└── skills/           # projectile and attack visuals
```

Planned (not fully implemented): skill-owned asset files under
`assets/skills/<id>/` (`icon.png` required, plus optional entity/particle
assets), configurable keybinding persistence/UI, loadout-editing UI, and the
HTML/mobile bridge.

## 5. Architecture invariants

These rules are mandatory. Breaking them requires updating
`docs/ARCHITECTURE.md` and justifying the change in the commit.

1. **`enzo-core` is pure.** It must not import `macroquad`, `wasm-bindgen`,
   `web-sys`, `std::fs`, `std::time`, `std::env`, or `rand::thread_rng`.
2. **The core is the only source of truth.** Damage, collision, aura cost, XP,
   level-up, and victory are decided in the core. The client only translates
   input and pixels.
3. **Fixed 60 Hz tick.** `DT = 1.0 / 60.0`; rendering may interpolate, but it
   must never drive simulation.
4. **Commands are data.** `PlayerCommand` per player per tick. The core does
   not read the keyboard.
5. **Explicit, serializable state.** `WorldSnapshot` is the contract with
   rendering, save, and networking. Do not put logic in the snapshot.
6. **Determinism.** No clock, `thread_rng`, `HashMap`/`HashSet` in logic, or
   mutable global state. Use `Rng` with an explicit seed and `Vec`/`BTreeMap`.
7. **System order is a contract.** Respect the `World::step` order documented in
   `docs/ARCHITECTURE.md`.
8. **N players from the start.** `MAX_PLAYERS`, stable `PlayerId`, and
   `commands` indexed by player. Never assume a single player in the core.
9. **No networking in the MVP.** Do not add WebSocket, a server, or matchmaking
   without updating the scope in `docs/SPEC.md`.
10. **Standardized entities.** Player, enemy, and projectile are the same
    `Entity` with shared components (`Body`, `Health`, `Stats`, `Faction`/team,
    controller/locomotion/skills as applicable). Always create entities via
    `EntityStore::spawn(EntitySpec)`; do not create parallel structs with
    duplicated attributes or assemble `Entity` by hand in systems.
11. **Mechanics and skills have requirements.** Walking and SixSeven are
    mechanics outside skill slots; jump, dash, fly, melee, Mogging, and other
    slotted abilities are skills with `REQUIREMENTS` (entity type, level,
    attributes, equipment). The `World` orchestrates systems; it must not
    implement skill/movement behavior inline.
12. **Action slots are generic.** 4 slots (`ActionSlot`) have no fixed category:
    any available `SkillId` can occupy any slot. Category is UI metadata.
13. **Loadout is a core rule.** `slot → SkillId` lives in `enzo-core`, persists
    in saves, and appears in snapshots. The same skill must **never** occupy two
    slots; `Loadout::assign` swaps slots instead of duplicating, and saves are
    sanitized on load. The client does not decide what can be equipped.
14. **A skill is a module, not a special case.** Each skill has its own file in
    `skills/`, with `DEF`, typed state, `REQUIREMENTS`, and assets declared for
    `assets/skills/<id>/` (icon required). Identity uses a `SkillId` enum with a
    static registry and `match` dispatch; no `Box<dyn Skill>` and no loose skill
    logic in `World`.

## 6. Code conventions

- **All code must be in English.** This includes identifiers, module/file names,
  comments, doc comments, log/error messages, test names, assertions, and commit
  messages. User-facing UI copy must also be written in English by default and
  managed through the project's i18n/text system when localization is needed.
- Prefer small modules and pure functions. Each module has a single
  responsibility (see the table in `docs/ARCHITECTURE.md`).
- No `unwrap()`/`expect()` in library code. Use `Result` or `Option` and handle
  errors. In tests, `unwrap()` is allowed.
- Avoid `panic!` in the core; map parse errors must become `LevelError`.
- Use `f32` behind the `Scalar` alias when it makes sense, to allow a future
  migration to fixed-point.
- Do not add dependencies without a clear need. The core must stay lightweight;
  `serde` stays behind the `serde` feature.
- Keep code formatted with `cargo fmt`; do not reformat unrelated files in the
  same commit.
- Comments explain **why**, not the obvious. Document contracts and invariants,
  not every line.

## 7. Tests

Every game-rule change needs a test. At minimum:

- **Unit:** functions in `math`, `map`, `aura`, `progression`, `mechanics`, and
  `skills` (including `Loadout::assign`, `sanitize`, and requirements).
- **Scenario:** jump, collision, double-tap, 3-hit combo, Mogging, death, flag.
  Also cover slot/loadout behavior (swap/move, level/attribute/item locks,
  cooldown not bypassed by slot changes) where applicable.
- **Determinism:** same seed + same commands = same snapshot.
- **Regression:** a fixed bug gets a test that would have failed before.

Scenario harnesses live in `crates/enzo-core/tests/`. Use `enzo-sim` to
reproduce bugs without a browser.

Do not use `sleep` in tests. Advance ticks explicitly with `World::step`.

## 8. Commits

- **Do not commit unless the user explicitly asks.**
- Commits must be **incremental**, with one logical change per commit.
- Use Conventional Commits: `feat:`, `fix:`, `test:`, `docs:`, `refactor:`,
  `chore:`, `build:`.
- Write commit messages in English, in the imperative, and keep them short; use
  the body to explain *why* when needed.
- Include the test in the same commit as the change it covers.
- Never commit `target/`, `dist/`, `node_modules/`, or local saves.
- Examples:
  - `feat(core): add fixed-timestep world loop`
  - `test(core): cover aura alternation combo`
  - `fix(physics): resolve one-way platform landing`

## 9. Assets

- Sprites must be original, pixel-art, and generated by
  `scripts/gen-sprites.mjs`.
- Do not copy characters, sprites, music, or names from existing works
  (Dragon Ball, Mario, etc.). The name "Mogging" belongs to this project.
- New assets go in `assets/` with the script that generates them versioned.
- If you replace a PNG, keep the atlas and dimensions documented.
- Planned skill assets live in `assets/skills/<id>/`: `icon.png` required and
  entity/particle assets optional, declared by the skill definition.
- Every `SkillId` needs an icon readable at 32 px. Do not keep a skill asset
  list parallel to the skill definition.

## 10. What NOT to do

- Put game rules in `enzo-wasm`.
- Read keyboard, clock, or files inside `enzo-core`.
- Duplicate the same `SkillId` in two slots or let the client validate loadouts.
- Create skills outside `skills/` or declare skill assets outside
  `assets/skills/<id>/`.
- Use `f32` for network decisions that require bit-exactness (multiplayer is
  authoritative by snapshot; if it becomes lockstep, migrate to fixed-point).
- Create global state, `lazy_static`, or mutable singletons in the core.
- Add multiplayer, audio, menus, or new levels without updating scope.
- Make a giant commit mixing refactor, feature, and formatting.

- [ ] `cargo test --workspace` passes.

- [ ] `docs/SPEC.md` and `docs/ARCHITECTURE.md` remain accurate.
- [ ] The core did not gain a render/wasm/IO dependency.
- [ ] The commit is incremental and follows the message convention (when the
      user explicitly asks you to commit).
