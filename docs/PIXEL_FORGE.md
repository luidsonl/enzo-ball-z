# pixel-forge — Asset Development Framework

> Project-local framework for developing **sprites, animations, rigs/layers,
> blocks, entities, and skill visuals** for EnzoBallZ.
>
> Status: **incremental implementation**. The framework starts with deterministic
> block/tile generation and validation; character rigs, layered customization,
> animation manifests, and broader entity/skill pipelines follow.

## 1. Purpose

`pixel-forge` provides a reproducible, contract-first workflow for game assets:

- Define assets and rules as **data contracts** (rigs, clips, layers/slots,
  visual definitions, block definitions, skill visual manifests).
- Generate or normalize spritesheets/manifests deterministically.
- Validate contracts before assets reach the game.
- Keep generated/runtime assets **outside the wasm binary** (`assets/` /
  `dist/assets/`) so they can be reused by the web UI, tooling, and future
  clients.
- Keep **gameplay rules authoritative in `enzo-core`**. `pixel-forge` handles
  presentation data/assets only.

## 2. Core principles

- **Contract-first:** every sprite/animation/layer must fit a rig or definition
  (cell size, clip names, frame count/order, pivot, slot, coverage/fallback).
- **Contract from code when authoritative:** gameplay rules (block
  collision/traversability, resistance, special hooks, skill requirements,
  stable IDs/symbols) are defined by `enzo-core`. `pixel-forge` should consume
  exported/generated definitions from that contract for asset generation and
  validation, avoiding duplicated gameplay data.
- **Deterministic outputs:** procedural generation (palette swaps, placeholders,
  sheets, manifests) produces stable results from the same inputs.
- **Original assets only:** follow `AGENTS.md`; do not copy protected characters,
  sprites, or styles from existing works.
- **Hybrid authoring:** procedural/code for structure, variants, placeholders,
  icons, tiles, and validation; manual pixel art (Aseprite/LibreSprite) for
  expressive character animation and detailed overlays.
- **Runtime composition:** the client composes layered characters at runtime
  (`base + equipment/cosmetic layers`) using stable IDs from core
  snapshot/save/UI contracts, never texture paths in `enzo-core`.
- **Validation before scale:** add new content by adding definitions/assets that
  pass the contract.

## 4. Contracts

### 4.1 Block definition (visual + gameplay-facing data split)

Gameplay behavior is owned by `enzo-core` (collision/traversability, fluid,
climbable, trigger, resistance). Visual data is owned/rendered by the client and
can be generated by `pixel-forge`.

A block definition should be able to represent:

| Field | Purpose | Example |
|---|---|---|
| `id` | Stable block identifier | `ground`, `crate` |
| `symbol` | ASCII map symbol | `#`, `D` |
| `size` | Cell footprint | `1x1` (`TILE_SIZE`) |
| `collision` | Movement/collision kind | `solid`, `platform`, `fluid`, `climbable`, `passable`, `trigger` |
| `resistance` | Durability when applicable | `none`, `{ hits: 3 }`, `unbreakable` |
| `special` | Core behavior hook | `none`, `swim`, `climb`, `goal_trigger` |
| `render` | Visual/render mapping | tile frame id, state frames, animation |
| `states` | Visual states | `intact`, `damaged_1`, `damaged_2`, `broken` |

Destructible blocks need **stateful visuals**. The core decides state (HP /
damage / destroyed); the renderer selects a frame/state from snapshot/runtime
state.

### 4.2 Character rig contract

A rig defines how all character layers align:

- `cell`: frame size (currently 32x32 for actors).
- `pivot`: origin reference for alignment/effects.
- `clips`: animation clips with frame count, duration/fps, loop/one-shot.
- `slots`: draw order and composition rules (`order`, `hiddenBy`, required,
  fallback behavior).
- `anchors` (optional): hand/muzzle/fx points per clip/frame (useful for
  Nutella gun, SixSeven hand poses, held items).

All layers for the same rig must share compatible grid/frame mapping.

### 4.3 Clip contract

Clips are logical animations, not raw file names:

- `idle`, `walk`, `run`, `jump_rise`, `jump_fall`, `dash`, `hurt`, `dead`
- combat/cast: `melee_1..3`, `cast_*`
- mechanics: `sixseven_a`, `sixseven_b` (or an equivalent state-driven clip)

Each clip declares: `frames`, `fps`/`frameDurationMs`, `loop`, and optional
events/anchors.

### 4.4 Layer/slot contract

Example slots (MVP subset can be smaller): `back`, `hair_back`, `body/skin`,
`pants`, `shoes`, `torso`, `armor`, `face_base`, `expression`, `hair_front`,
`headgear`, `weapon`, `front_fx`.

Rules are explicit and data-driven:
- `headgear` may hide `hair_front` or select an alternate variant.
- `expression` is chosen from gameplay/visual state (`hurt`, `attack`, `cast`,
  `idle`) with fallback.
- `weapon` visuals can vary by clip; gameplay projectiles (e.g. Nutella shot)
  remain separate entities/sprites.

### 4.5 Visual definition

A visual definition binds a stable ID to a rig/slot/source:

- `id`: `weapon.nutella_gun`, `headgear.cap_red`, `expression.hurt`
- `rig`: `enzo_32`
- `slot`: `weapon`
- `covers`: clips covered by this visual
- `source`: authored or generated sheet path
- `fallback`: visual/slot fallback when missing
- `variants`/`palette`: recolor variants (skin, hair, clothing)

## 5. Sprite and animation creation workflows

### 5.1 Procedural (code)

Use Node generators for deterministic assets:
- tiles/blocks and simple state variants;
- icons, placeholders, particles, simple effects;
- palette swaps/recolors for skin, hair, and clothing;
- spritesheet assembly and manifest generation.

This is the same family of approach as ``node tools/pixel-forge/cli.mjs` (modular assets)`, but moved
behind framework contracts.

### 5.2 Manual (Aseprite/LibreSprite)

Use a pixel editor for expressive or detailed art:
- draw frames on the rig grid with consistent pivot/alignment;
- organize clips/tags to match the contract;
- export PNG spritesheets to `assets/authored/`;
- register the visual definition and run validation.

### 5.3 Hybrid

Most character customization is hybrid:
- manual base/poses/overlays for quality;
- procedural recolors/variants/manifests/validation for scale.

## 6. Runtime integration

- **`enzo-core`** exposes stable IDs/state (block kinds/state, equipment/visual
  IDs, skill/entity state). No PNG paths or render details.
- **`enzo-wasm`** resolves IDs to textures/frames via manifest/registry and draws
  tiles, layered characters, and skill VFX/entities.
- **`web`/Vue** may reuse the same manifests/asset URLs for previews/UI, but
  never computes gameplay rules.

## 7. Framework model: pipeline + scaffolder

`pixel-forge` should combine two complementary roles:

### 7.1 Asset pipeline (build/validate/inspect)

Consumes contracts/definitions and produces or validates assets:

```bash
node tools/pixel-forge/cli.mjs build blocks
node tools/pixel-forge/cli.mjs build rigs
node tools/pixel-forge/cli.mjs validate blocks
node tools/pixel-forge/cli.mjs validate rigs
node tools/pixel-forge/cli.mjs inspect block crate
node tools/pixel-forge/cli.mjs inspect compose --rig enzo_32 --clip sixseven_a --frame 0
```

### 7.2 Scaffolder (Artisan/Nest-like)

Generates standardized files/stubs for new content, similar to Artisan or Nest
module generators, but aligned with EnzoBallZ contracts:

```bash
pixel-forge generate block crate --symbol D --solid --hits 3
pixel-forge generate skill nutella-shot --category attack --source equipment
pixel-forge generate visual weapon.nutella_gun --rig enzo_32 --slot weapon
pixel-forge generate rig enzo_32 --cell 32 --clips idle,run,jump,sixseven_a
```

A generator may create or guide updates to:
- canonical visual/asset definitions (`assets/definitions/...`);
- deterministic placeholder sprites/states (e.g. crate intact/damaged frames);
- manifest entries and validator coverage;
- core registration stubs when appropriate (following existing Rust patterns;
  gameplay remains explicit in `enzo-core`, not hidden magic);
- test skeletons or TODO markers for required gameplay/render integration.

The scaffolder must **not** become a second gameplay source of truth. It should
produce code/data consistent with the authoritative contract and the project's
architecture rules.

Convenience npm scripts should wrap stable commands (e.g. `sprites:blocks`,
`sprites:validate`).

## 8. Validation

Validators should fail fast on:
- wrong image dimensions or non-rig cell multiples;
- missing/extra clip frames or wrong frame order assumptions;
- unknown IDs, duplicate block symbols, or invalid slot/rule references;
- missing required assets (skill icons, required base layers);
- visual coverage gaps without fallback;
- manifest/source path mismatches.

## 9. Current implementation focus

The first implementation slice is **blocks**:
- data-driven block visual definitions;
- deterministic tile sheet generation (including destructible block states);
- manifest output for block render frames;
- validators for block definitions/frame sizes;
- integration path for `enzo-core` destructible block behavior and `enzo-wasm`
  rendering.

Character rigs/layer composition and full skill visual pipelines come after the
block foundation and framework CLI are stable.
