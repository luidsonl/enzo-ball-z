# EnzoBallZ — Architecture and Harness

> Architecture document for the project. It defines code boundaries, the
> simulation contract, the WASM build pipeline, and the test harness. The goal
> is for `enzo-core` to run without changes in the browser (client), in headless
> tests, and, in the future, on an authoritative server.
>
> **Audit note (2026):** The core has migrated to action slots and modular
> skills (`Locomotion` + `Skills`, `PlayerCommand` with `slots[4]`,
> `SNAPSHOT_VERSION = 3`, `SAVE_VERSION = 2`). The client has been adapted and
> render has been modularized. A DOM UI layer now exists (`web/ui/*`) backed by
> Rust `ui_bridge`/`ui_controller` (`UiState` + semantic actions/loadout actions),
> covering menus, in-game HUD tabs/panels (including Status point distribution and
> Skills assignment for unlocked skills), and mobile controls. Remaining/planned
> work includes full keybinding persistence/UI, skill-owned asset pipeline, richer
> loadout/action-bar UX (locks/toasts/icons/pause polish), and a possible migration
> of the DOM UI implementation to Vue/Vite. Where this document describes planned
> work, it is labeled explicitly.

## 1. Principles

1. **The core is the only source of truth.** Game rules, physics, map, combat,
   aura, and progression live in `enzo-core`. The client draws and collects
   input; it does not decide rules.
2. **Pure core.** `enzo-core` does not depend on `macroquad`, `wasm-bindgen`,
   `web-sys`, files, system clock, or global randomness.
3. **Fixed tick.** Simulation advances in steps of `1/60 s`. Rendering may run
   at any rate and interpolate between ticks.
4. **Commands as data.** Each player produces a `PlayerCommand` per tick. The
   source can be local keyboard, AI, or network without changing the core.
5. **Authoritative server (future).** Multiplayer will use server snapshots, not
   lockstep. The client sends commands and receives state; prediction and
   reconciliation come later. This avoids requiring bit-exactness across
   architectures.
6. **No third-party assets.** Sprites are original and generated by script.

### 3.1 Standardized entity model

Player, enemies, and projectiles are the **same** `Entity` type. What changes is
the `EntityKind`/specific data; shared attributes live in common components.

Conceptual shape (current implementation uses `Locomotion` + `Skills`):

```rust
pub struct Entity {
    pub id: EntityId,
    pub kind: EntityKind,       // Player | Enemy | Projectile | Item
    pub controller: Controller, // Player(...) | Ai(...) | None
    pub team: TeamId,           // PLAYERS | ENEMIES | NEUTRAL
    pub body: Body,             // position, velocity, size, facing, on_ground
    pub health: Health,         // current health + i-frames
    pub stats: Stats,           // speed, strength, max health, max aura, etc.
    pub attributes: Attributes, // character points
    pub equipment: Equipment,   // equipped item modifiers/tags
    pub locomotion: Locomotion, // walk, sixseven (non-slot mechanics)
    pub skills: Skills,         // loadout + per-skill runtime state/cooldowns
}
```

Key rules:

- `Stats` is derived from attributes for the player and fixed/configured for
  enemies; both use the same struct.
- `EntityStore` is the only creation/removal point:
  `spawn(EntitySpec)`, `despawn(id)`, accessors, and deterministic iteration.
- `EntitySpec` provides explicit constructors (e.g., player, slime/enemy,
  Mogging/projectiles, items). Systems do not assemble `Entity` by hand.
- The store uses deterministic iteration (e.g., `BTreeMap<EntityId, Entity>`)
  and stable IDs. IDs are not reused in the MVP.
- Systems must not duplicate attributes: damage, health, speed, and team come
  from common components/data.
- `Controller` owns intent state: player controller stores tick input intent; AI
  stores behavior/state; `None` covers projectiles/items.
- Slotted abilities are skills with requirements (`EntityType`, level,
  attributes, equipment tags). `Loadout`/skills logic enforces availability and
  uniqueness.
- Walking and SixSeven are not skill slots.

### 3.2 `World::step` system order

Order is part of the contract: changing it changes replay/network behavior.

1. **input**: apply `PlayerCommand` to player controllers (`move_x`, `move_y`,
   slot inputs, SixSeven, meta fields as applicable).
2. **sixseven**: consume `6`/`7` intent and update aura/combo/slowdown.
3. **skills pre-physics**: walk intent, jump buffer, dash request, fly vertical
   intent, and other pre-physics skill behavior.
4. **physics**: integrate bodies and resolve tile collisions (X, then Y).
5. **skills post-physics**: melee, Mogging, Nutella shot, shout, and other
   post-physics skills (hitboxes/projectiles use integrated positions).
6. **projectiles**: move projectiles and resolve tile/enemy collisions.
7. **ai**: patrol and enemy intent.
8. **collisions**: contact damage, i-frames, knockback.
9. **skills tick/cooldowns/timers**: advance skill cooldowns and internal timers.
10. **progression**: grant XP, level up, create points.
11. **cleanup**: remove dead entities and expired projectiles.
12. **events**: return the tick event list.

> Implementation detail note: exact helper boundaries may live in `world`,
> `mechanics`, or `skills`; the externally important part is the deterministic
> pipeline and behavior. Any order change requires updating docs and determinism
> tests.

## 4. Simulation contract

```rust
pub const TICK_HZ: u32 = 60;
pub const DT: f32 = 1.0 / 60.0;
pub const MAX_PLAYERS: usize = 4;

pub struct SlotInput {
    pub pressed: bool, // edge for the tick
    pub held: bool,    // continuous state
}

pub struct PlayerCommand {
    pub move_x: i8,  // -1, 0, 1
    pub move_y: i8,  // -1, 0, 1 (fly/vertical intent)
    pub slots: [SlotInput; ActionSlot::COUNT], // 4 generic slots
    pub sixseven: Option<SixSevenKey>,
    pub allocate: Option<Attribute>,
    pub confirm: bool,
    pub restart: bool,
}

pub struct TickInput {
    pub commands: [Option<PlayerCommand>; MAX_PLAYERS],
}

pub struct TickOutput {
    pub events: Vec<GameEvent>,
}
```

- `World::step(&mut self, input: TickInput) -> TickOutput` is the only time
  advancement entry point.
- `World::snapshot() -> WorldSnapshot` is pure/read-oriented over current state.
- `World::write_snapshot(&mut WorldSnapshot)` fills an existing buffer and
  reuses `entities` so the client does not allocate every tick.
- `PlayerId` is stable and indexes `commands`; absent players are `None`.
- `pressed` fields (slot presses, `sixseven`, `allocate`, `confirm`, `restart`)
  are **edge-triggered**. The client computes edges; the core does not know
  browser key repeat.
- The core stores `tick: u64` and an `Rng` with an explicit seed. Nothing reads
  the system clock.
- Loadout changes are a core API (`World::apply_loadout(LoadoutRequest)`), not a
  `PlayerCommand` field, because they are sparse and typically applied while
  paused.

### Determinism

- Forbidden: `std::time`, `rand::thread_rng`, `HashMap`/`HashSet` in logic,
  nondeterministic iteration, mutable global state.
- Allowed: `Vec`, `BTreeMap`, `f32` behind the `Scalar` alias.
- **Trade-off:** the MVP uses `f32` (`type Scalar = f32`). Tests and replays are
  deterministic on the same platform. Because multiplayer is authoritative by
  snapshot, bit-exactness across wasm and x86 is not required. If lockstep is
  needed later, switch `Scalar` to fixed-point without changing signatures.
- Determinism test: two `World`s with the same seed and the same `TickInput`
  sequence (and same `LoadoutRequest` sequence, when applicable) must produce
  identical snapshots (hash) after N ticks.

## 5. Snapshot and serialization

```rust
pub const SNAPSHOT_VERSION: u16 = 3;

pub struct WorldSnapshot {
    pub version: u16, // SNAPSHOT_VERSION
    pub tick: u64,
    pub phase: GamePhase,
    pub phase_timer: f32,
    pub entities: Vec<EntitySnapshot>,
    pub level_width: f32,
    pub level_height: f32,
    pub flag: Option<Rect>,
    pub camera_hint: Vec2,
}
```

- `WorldSnapshot` contains no logic; it is the contract between core and
  render/network.
- Player snapshots include progression/loadout and skill slot/catalog data used
  by the UI (read-only on the client).
- `serde` stays behind the `serde` feature in `enzo-core` to keep the core
  lightweight.
- JSON is used for debug/save/tests where appropriate; compact formats
  (`postcard`/`bincode`) can be used for networking in the future.
- `version` is bumped on incompatible changes. Snapshots are not persisted, so
  migration is not required; all consumers must compile against the current
  version.
- The renderer never mutates the snapshot or `World` directly.

## 6. WASM client (`enzo-wasm`)

### Loop

```text
accumulator += frame_dt
ticks = min(floor(accumulator / DT), 5)
while ticks > 0:
    swap(previous, current)
    world.step(input_for_tick())
    world.write_snapshot(&mut current)   # reuses entity buffer
    accumulator -= DT
if accumulator >= DT: accumulator = 0     # drop slow-frame backlog
alpha = accumulator / DT
render(previous, current, alpha)
```

- `frame_dt` is clamped (e.g., 0.2 s) to avoid the spiral of death.
- At most 5 ticks per frame; excess time is dropped instead of creating a queue
  that stalls the next frame further.
- Rendering interpolates positions between previous and current snapshots using
  `alpha`; camera uses the same interpolated focus.
- Simulation never depends on framerate.

### Input mapping (current defaults)

| Action | Keys |
| --- | --- |
| Move | `A`/`D` or `←`/`→` |
| Up / fly intent | `W`/`↑` (`move_y = -1`) |
| Jump (also) | `W`/`↑` also triggers slot 1 press (QoL mapping) |
| Skill slot 1 | `Space` (default: Jump) |
| Skill slot 2 | `Left/Right Shift` (default: Dash) |
| Skill slot 3 | `J` (default: Melee) |
| Skill slot 4 | `K` (default: Mogging) |
| SixSeven (aura) | `6` and `7`, alternating |
| Distribute point | `1` Speed, `2` Strength, `3` Health, `4` Aura |
| Confirm level-up/UI | `Enter` |
| Open menu | `Esc` |
| Restart | `R` |

Mouse input is read once per frame by `pointer`, with edge-triggered clicks. It
is the primary path for menu/HUD; keyboard remains valid for accessibility and
keyboard users. Clicks produce UI actions; `app` translates them into core
commands or scene changes. No game rules live in the UI layer.

### Render, camera, and HUD

- `render/` draws the world from snapshots.
  - `render/world.rs` orchestrates drawing (tiles, flag, items, enemies,
    projectiles, players, generic effects).
  - `render/entities/*` owns character/entity body animation and drawing.
  - `render/skills/*` owns projectile and attack visuals/overlays.
  - `render/background.rs` handles background/parallax visuals.
- `tiles.rs` groups the map into chunks (e.g., 16×16 tiles). Visible chunks are
  built once as static meshes; off-camera chunks are not built.
- `camera.rs` follows the player with smoothing and clamps to map bounds.
- `ui.rs` contains shared visual primitives (panels, buttons, dots, text), mainly for canvas-rendered UI.
- `menu/` contains menu/screen logic as used by the client; DOM menus in `web/ui/menus.js` also render menu state from `UiState`.
- `hud/` contains canvas HUD/overlay modules. In addition, DOM HUD in `web/ui/hud.js` renders tabs/panels (Status point distribution, Equipment, Skills assignment for unlocked skills, Items), and DOM mobile controls live in `web/ui/mobile-controls.js`.
- `ui_bridge.rs` / `ui_controller.rs` expose semantic UI actions and polled `UiState` JSON to the DOM layer; the DOM layer must not compute game rules.
- `i18n.rs` stores `Text` keys and translations (pt-BR/en). Language is selected
  in the menu and persisted in `localStorage`; the core never formats UI text.
- `save.rs` stores versioned JSON in `localStorage` (save v2 with migration
  behavior). Language is stored separately (e.g., `enzoballz.language`).
- `sprites.rs` loads sprite atlases and provides shared sprite access.
  Skill-specific visual ownership is being modularized into render/skill modules;
  skill-owned asset loading under `assets/skills/<id>/` is planned.

### Golden rule

If a decision changes the game outcome (damage, collision, cost, XP, level-up),
it belongs in `enzo-core`. The client only translates input and pixels.

## 7. Build harness

### Toolchain

```bash
rustup target add wasm32-unknown-unknown
```

- `rust-toolchain.toml` pins the channel (1.92.0) and `wasm32-unknown-unknown`.
- The client uses the macroquad JS bundle; the build does not require
  `wasm-bindgen-cli`.

### Pipeline (`scripts/build-wasm.sh`)

```text
1. cargo build -p enzo-wasm --release --target wasm32-unknown-unknown
2. create dist/.nojekyll (GitHub Pages must not process the bundle with Jekyll)
3. copy wasm, HTML, JS plugins, and assets/ to dist/
4. result is a self-contained static site
```

### Local server (`scripts/serve.mjs`)

- Plain Node, no dependencies.
- Serves `dist/` with `Content-Type: application/wasm` for `.wasm`.
- Default port `8080`, configurable with `--port`.
- `npm run dev` = build + serve; `npm run build` = build only.

### Static hosting (GitHub Pages)

- `.github/workflows/pages.yml` compiles and publishes `dist/` via GitHub
  Actions.
- The bundle uses relative paths, so it works at root or under
  `https://user.github.io/repository/`.
- Pages does not run server logic or WebSocket. The static client is compatible
  with a future authoritative server because it only sends commands and renders
  snapshots.
- When multiplayer exists, the server URL must be read at runtime (config file),
  not hardcoded in the wasm, so the same artifact can target different servers.
- Adding networking requires updating the scope in `docs/SPEC.md` first.

### Alternative

`trunk` can replace the pipeline if the team prefers, but the path above is the
supported/tested MVP path.

### Build acceptance criteria

- `cargo test -p enzo-core` is green.
- `cargo clippy -p enzo-core -- -D warnings` is green.
- `npm run build` produces `dist/` and the game opens in the browser via
  `npm run dev`.
- Reloading the page restores the loaded slot's progression.

## 8. Test harness

### Pyramid

| Level | What it covers | Where |
| --- | --- | --- |
| Unit | math, map, aura, progression, mechanics/skills helpers | `#[cfg(test)]` per module |
| Scenario | jump, collision, combo, Mogging, death, flag, slot/loadout behavior (target) | `crates/enzo-core/tests/` |
| Determinism | same input + same seed = same hash | `tests/determinism.rs` (and related tests) |
| Headless (manual/CI) | run command/loadout sequences and print snapshots/hash | `enzo-sim` |

### Minimum scenarios

1. **Physics:** player falls, lands on ground, and does not pass through solid
   tiles.
2. **Jump:** jump only when allowed; coyote time and jump buffer respected.
3. **Run:** double-tap within the window starts running; releasing cancels.
4. **Aura:** alternating `6,7,6,7` increases aura; repeating a key resets combo;
   without farming, the combo expires and slowdown ends.
5. **Melee combo:** three presses within the window apply 3 hits; third applies
   knockback; outside the window it restarts.
6. **Mogging:** not enough aura does not fire; with aura it consumes cost, hits
   enemies, and disappears on solid tiles.
7. **Progression:** enough XP levels up, grants 1 point, and pauses.
8. **Attributes:** each point changes the correct derived stat.
9. **Death:** HP 0 -> respawn at start, full health/aura, XP/level kept, enemies
   respawn.
10. **Victory:** touching the flag -> victory phase, save written.
11. **Loadout/slots (target coverage):** swap/move/clear, level/attribute/item
    locks, cooldown not bypassed by slot changes, save v1→v2 migration, and slot
    activation behavior.

### `enzo-sim`

```bash
cargo run -p enzo-sim -- --script tests/replays/basic.json --ticks 600
```

- Reads a `TickInput` sequence from JSON, runs the core, and prints snapshots
  (or a final hash).
- Useful for debugging without a browser and for generating bug replays.
- Does not depend on macroquad, so it can run in CI.
- For full determinism with loadout changes, replays should support
  `LoadoutRequest` records applied at tick boundaries (planned/target format).

## 9. Multiplayer path

What is already prepared in the MVP/core design:

- `World` accepts `MAX_PLAYERS` commands per tick and uses stable player IDs.
- No game rule reads keyboard, clock, or globals.
- `WorldSnapshot` is serializable and versioned.
- System order is fixed and documented.
- `enzo-sim` proves the core can run outside the browser.

Deliberately out of MVP scope:

- Server, WebSocket, matchmaking, authentication, anti-cheat.
- Client prediction, reconciliation, remote interpolation.
- Server-side progression persistence (MVP uses `localStorage`).

Future design:

```text
Client A ──commands @ 60 Hz──▶ Authoritative server (enzo-core)
Client B ──commands @ 60 Hz──▶   ├─ step @ 60 Hz
                                 └─ snapshots @ 20 Hz ──▶ clients
```

- `enzo-server` reuses `enzo-core` and a network `CommandSource`.
- Client applies snapshots and interpolates; local prediction is added only if
  latency justifies it.
- Save moves to the server; `localStorage` becomes cache/offline.
- Loadout changes become reliable/sequenced messages (`LoadoutRequest`), not
  movement commands.

## 10. Risks and open decisions

| Risk | Mitigation |
| --- | --- |
| `f32` is not bit-exact across wasm/x86 | Authoritative snapshot multiplayer; `Scalar` alias allows fixed-point later |
| Toolchain/build drift | Pin in `rust-toolchain.toml` + build script checks |
| Large/slow wasm build | `opt-level = "s"`, `lto = true`, `codegen-units = 1` in release profile |
| Generated sprites look bad | Versioned generator; replace PNGs later without touching core |
| Save breaks across versions | Versioned JSON + explicit migration or safe reset |
| Scope creep (more powers/levels) | `SPEC.md` lists non-goals; new abilities enter as skill modules, not loose `World` logic |
| HTML UI duplicates rules | HTML emits actions and renders `UiState` only |
| Missing skill assets | Placeholder + log; host existence test; no panic |

## 12. Planned evolution: keybindings, loadout/UI polish, skill assets, DOM UI (Vue/Vite migration candidate)

> Partially implemented in core/client (see audit in `ACTIONS_AND_SKILLS.md`).
> This section tracks remaining architectural integration work.

The target is to keep these layers separated:

1. **Physical key** (`enzo-wasm`/HTML/DOM): `KeyCode`, touch button, gamepad.
2. **`InputAction`** (`enzo-core::input`): stable semantic vocabulary.
3. **Loadout** (`enzo-core::skills`): which `SkillId` occupies each of the 4
   slots.
4. **Skill** (`enzo-core::skills`): requirements, state, activation, cost,
   cooldown, and assets.

Current DOM bridge (implemented in parts):
- Rust exports (`ui_bridge.rs`) provide `enzo_action_down/up`, `enzo_ui_action`,
  `enzo_loadout_assign/clear`, and polled `UiState` JSON (`enzo_ui_state_ptr/len`).
- `ui_controller.rs` publishes state and consumes semantic UI actions; core rules
  remain authoritative.
- `web/ui/*` renders DOM menus, HUD/panels, and mobile controls. The bridge uses
  `#[no_mangle] extern "C"` exports (no `wasm-bindgen`/`web-sys`).

Remaining/planned integration work:

- `KeyBindings` model + `enzoballz.bindings.v1` persistence + rebind UI.
- Loadout/UI polish: richer action bar, lock reasons/toasts, icon/cooldown/aura
  feedback, pause/loadout-edit UX, and full skill catalog presentation.
- Skill-owned asset files under `assets/skills/<id>/` generated and loaded; move
  skill-specific fx/frame ownership out of shared generic handling where
  appropriate.
- **Vue.js + Vite migration (planned, if adopted):** migrate `web/ui/*` DOM view
  layer to Vue components while preserving the Rust bridge contract (`UiState`,
  semantic actions, loadout actions, virtual input). Build pipeline (`dist/`),
  miniquad plugin/script ordering, and web tests must be updated accordingly.

All core invariants from section 1 still apply. HTML/DOM must never calculate
game rules or read/write authoritative saves.
